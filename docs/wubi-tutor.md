# 五笔练习室（Wubi Tutor）

阿渺工具箱内的一个练习工具，帮助已会拼音打字的用户学会五笔字型输入法。

---

## 1. 模块定位

**是什么**

- 一个**练习**工具：认字根 → 记键位 → 拆字 → 打单字 → 打词组 → 打文章
- 一个**查码**工具：汉字 ↔ 编码互查，含重码候选
- 一个**进度**工具：课程闯关、错题本（间隔重复）、成绩趋势、成就

**不是什么**

- **不是输入法**：不接管系统输入，不产生候选框，只在工具内练习
- **不是字典**：码表按练习频次裁剪（见 §3），生僻字可能查不到
- **不是独立工具**：作为练习室内的 5 个 Tab 实现，**不注册为独立工具入口** ——
  避免工具列表膨胀，也避免码表在多个入口重复加载

**5 个 Tab**

| Tab | 职责 | 是否依赖码表 |
|---|---|---|
| 学习 | 字根图、教程、规则速查卡 | 否 |
| 练习 | 7 种练习模式 + 课程闯关 + 今日计划 | 是 |
| 复习 | 错题本与间隔重复队列 | 是 |
| 查码 | 汉字 ↔ 编码互查 | 是（含词组表） |
| 成绩 | 趋势图、坚持指标、里程碑、成就墙 | 否（读本地统计） |

## 3. 生成物与再生成

### 生成物清单

```
miao-toolbox-web/src/modules/tools/wubi-tutor/data/generated/
├── chars.json           单字表（含全码 / 简码等级）
├── phrases-2.json       二字词
├── phrases-3.json       三字词
└── phrases-4plus.json   四字及以上
```

词组**按长度拆成 3 个独立 chunk**，而不是一个大文件 ——
练习模式选定长度后只加载对应那块（练习二字词只需 90KB，不必拉全量）。

### 再生成步骤

```bash
# 1) 拉取上游快照（写入 scripts/data-sources/）
node scripts/fetch-wubi-dict.mjs

# 2) 由快照生成码表（含体积裁剪）
node scripts/build-wubi-tables.mjs

# 3) 校验拆字覆盖率
node scripts/verify-wubi-split.mjs
```

**没有网络时**可用样本数据跑通全流程（仅 60 余字，仅供开发）：

```bash
node scripts/build-wubi-tables.mjs --sample
```

> `--sample` 会**覆盖**真实生成物，用后记得重新执行正式构建。

### 体积裁剪为什么必要

上游词表包含 61205 条词组，其中二字词 37879 条 —— 绝大多数是学习者
一辈子不会打的组合。单字表同理（生僻字占了大量体积）。

构建脚本按「简码优先 + 词频」排序后，**用二分查找确定能装进预算的最大条数**，
而不是写死一个条数：

| 产物 | 条数 | gzip（产物实测） | 预算 |
|---|---|---|---|
| `chars.json` | 12452 | **98.39 KB** | ≤ 100 KB |
| `phrases-2.json` | 10558 | **89.92 KB** | — |
| `phrases-3.json` | 3024 | **31.58 KB** | — |
| `phrases-4plus.json` | 2122 | **27.62 KB** | — |
| 词组合计 | — | **149.12 KB** | ≤ 300 KB |

被裁掉的是长尾组合，**GB2312 常用字（6763 字）覆盖完整**，构建脚本会校验这一点。

### ⚠️ 两处容易踩的坑（改构建脚本前务必读）

1. **不要给 `entries` 按拼音排序。**
   数组顺序承载「常用度降序」语义，查码页的重码候选直接按该顺序输出。
   曾为「便于 diff」加过拼音排序，结果重码列表变成无意义顺序 —— 且编译、
   单测、页面全都正常，只有用户看到怪异的候选顺序才会发现。
   `dataContract.test.ts` 有针对此的回归测试。

2. **构建脚本报的是「原始 JSON gzip」，不是产物 chunk gzip。**
   rollup 会加 ESM 包装并重序列化，产物比原始 JSON 大 3~5%。
   脚本按 95% 折扣做保守判断（`EMITTED_OVERHEAD_RATIO`），
   **权威口径在 `scripts/check-wubi-tutor.sh`** —— 它直接量 `dist/assets/*.js`。
   曾因此出现「脚本报 98.4KB 通过、构建报 101.95KB 超预算」的分裂。

## 4. 性能基线（Story 5.3 实测）

| 指标 | 目标 | 实测 | 说明 |
|---|---|---|---|
| 工具主包 | ≤ 60 KB gzip | **45.18 KB** | `WubiTutorPage-*.js` |
| 单字码表 | ≤ 100 KB gzip | **98.39 KB** | 独立 chunk，按需加载 |
| 词组表 | ≤ 300 KB gzip | **149.12 KB** | 3 个独立 chunk |
| 输入延迟 | ≤ 50 ms | **0.10 ms/键** | 会话状态机同步成本，见下 |
| 拆字覆盖率 | ≥ 95% | **100%** | 12452 / 12452 |

**输入延迟的测量口径**：`perf.test.ts` 量的是 `handleAnswerKey` + 题源推进的
同步 CPU 成本（React 渲染与 DOM 提交另计，通常 1~3ms）。测试用
`QUESTION_POOL = 5000`（远大于应用实际的 `ROUND_SIZE = 20`），
候选池越大推进越慢，因此该数字是**生产环境的保守上界**。

**码表不在首屏**：`chars.json` / `phrases-*.json` 全部走动态 `import()`，
只在进入练习 / 复习 / 查码 Tab 或打开拆字演示时才拉取。
学习 Tab（字根图 / 教程 / 速查卡）完全不加载码表。

> 曾有一个隐蔽的破坏点：`SplitDemo` 一度**静态** import 了 `chars.json`，
> 使 13 万条码表被并进主包（主包 gzip 148KB），Story 3.1 的懒加载门控
> 完全失效。构建时会有 `INEFFECTIVE_DYNAMIC_IMPORT` 警告，**不要忽略它**。

## 5. 指标口径

「题」与「字」在五笔练习里是两回事，所有统计都按下面的规则换算：

| 练习模式 | 一题 = 几字 | 说明 |
|---|---|---|
| 单字 / 简码 | 1 | |
| 词组 | 2 ~ 6 | 按词组实际长度 |
| 文章 / 自定义文本 | 整篇可打字数 | 整篇算**一道**题 |
| 键位 / 字根认知 / 字根输入 | **0** | 不涉及汉字 |

由此产生三条用户可见的结论：

- **「累计字数」只统计真正打出来的汉字**。键位与字根练习不计入
  （此前它们被当成 1 题 1 字，导致一个字没打也能"累计几百字"）。
- **速度单位随模式而变**：上表前三类是「字/分钟」，后一类是「题/分钟」
  （界面上的单位会跟着切换）。实时速度按**码长均摊**——
  一个四码字每键贡献 1/4 字，因此数值是平滑的，不会在完成那一刻跳一下。
- **课程通关的「完成 ≥ 20 字」**同样按上表换算；字根类环节不含汉字，
  会回退成「完成 ≥ 20 题」。

> ⚠️ 历史数据：`DailyStat.correctChars` 早期用「完成题数」填充，
> 旧记录里键位 / 字根练习的字数被虚增、词组被少算。
> 该偏差只影响历史累计值，不做迁移（迁移需清空学习数据，代价大于收益）。

### 关卡出题口径（三个环节各练什么）

每键一关，固定三个环节，出题范围逐层收窄到「用户真的学过的东西」：

| 环节 | 出什么 | 依据 |
|---|---|---|
| 字根认知 | 已学键范围内的字根 → 按出所属键 | `getLearnedKeys` |
| 字根编码 | 本关字根 → 打出它的**完整编码**（王 `gggg`、五 `gghg`、一 `ggll`） | 成字字根取码规则 |
| 单字练习 | 本关字根中能独立成字者 ∪ 只用已学键能拼出的字 | `getLessonCharPool` |

**三条不能破的约束**（都有回归测试守着）：

1. **字根编码的答案必须逐字不同。**
   早期复用了 `createRadicalSequenceSource({ keys: [lessonKey] })`，而它的答案取
   「字根所属键」—— 单键关卡下每个字根的 key 都是同一个字母，
   **答案恒为 `gggg`**，题面却显示「王 青 戋 五」。用户按 4 次 G 就过关，
   等于在教「所有 G 键字根都打 G」这条**错误规则**。

2. **单字池里每个字的编码都不得用到未学键。**
   这是「不出现没学过的字根」的形式化表达。唯一允许的例外是
   「成字字根取码规则」自身的用键：五个区内首笔键 `g/h/t/y/n`
   加补位键 `l`（如 一 = GGLL），否则连本关的字根都练不到。

3. **不能把「五个首笔键」整体当成已学。**
   看似合理（成字字根规则确实要用它们），但 H/T/Y/N 上还有**真实字根**
   （止、攵、广、己…）。一放开，G 关就会混进「政 = 一+止+攵+丶」。

**「借字表示的部件」要单独识别。**
字根数据用 `glyph` 记录部件，有些部件本身是汉字但**并非成字字根** ——
例如 G 键的「青头」记作 `'青'`，而 青 = `gef` 要用 月(E)、土(F)。
判别方式是看编码是否符合成字字根规则（`questionSource.isRadicalCode`）：
青 不满足，因此它只能出现在「字根认知」环节（认出它在哪个键），
不进入「字根编码」与「单字练习」。

**码表里的生僻字。**
12452 条中有 **1848 条（14.8%）**是扩展区 / 兼容汉字（`䜣`、`㣺`、`𩂊`…），
其中一部分是代理对（JS 里 `length === 2`），会破坏「一个字 = 一个字符」的
假设。出题与统计统一用 `questionSource.isPracticableChar` 过滤。

### 简码：打完后必须能按空格提交

`Question.altAnswers` 承载简码（五 = `gg`、一 = `g`），但它只做**逐位备选** ——
**短答案在结构上无法提交**。

完成判定是 `inputKeys.length >= answerKeys.length`（必须打满全码），
所以打完 `gg` 后状态机仍在等第 3 位 `H`。如果只提示「有二级简码 gg」
而不实现提交路径，用户打完 gg 就会被判「按错了，正确是 H」——
**提示与实现互相矛盾**。

正确做法（已实现，见 `session.confirmShortAnswer`）：
**打满全码自动上屏，打完简码后按空格出字** —— 与真实五笔一致。由此派生四条约束：

- 提示文案必须写明「打完按空格出字」，否则等同于误导；
- 空格**不计入击键数**（准确率衡量的是编码字母，不是确认键）；
- 错误态下空格等同提示里的「任意键」：只清错误态、不推进输入
  （否则用户按空格毫无反应，会以为界面卡住）；
- 两条上屏路径（全码自动 / 简码确认）共用 `advanceAfterCorrect`，
  否则同一个字会因提交方式不同而统计出两套结果。

> 另：`WubiFinger`（`'r-index'`）是内部枚举，**界面必须经
> `FINGER_LABELS` 转成中文**（右食指）。直接渲染会漏出英文标识。

### 拆字演示：为什么是「对照视图」而不是「唯一拆分」

拆字演示给出的是**逐位键位 + 该键全部候选字根**，由用户对照字形挑选，
而不是一个自动推出的「唯一拆分」。这是能力边界，不是偷懒：

**汉字无法做字形包含判断。**

```
'的'.length = 1
'的'.includes('白') === false      // 汉字是单个码位，永远不包含另一个汉字
```

所以「字根是否是字形的子串」这条判据对汉字**恒为 false**（含变体映射），
只剩「字根 === 该字」一条有效。早期实现以此为唯一算法，
结果是 12452 个字里只有 **25 个（0.2%）**能推出拆分，
其余全部显示「暂不支持」—— 连「一」这种最基本的字根都不例外。

**唯一拆分需要一张字根分解表**（`char → 字根序列`），
而上游码表只有 `字\t编码\t词频` 三列，没有这份数据。

因此当前拆分为三态（`splitter.ts`）：

| 状态 | 含义 | 覆盖 |
|---|---|---|
| `resolved` | 每一位都能确定 | 121 个（1.0%）—— 键名字 + 成字字根，走**取码规则**可推（含补位位） |
| `ambiguous` | 每位都有候选字根，需对照字形挑选 | 12331 个（99.0%） |
| `unsupported` | 某位在该键上找不到字根（数据缺失） | 0 |

**验收口径**：`unsupported = 0`（见 `splitter.coverage.test.ts`）。
它由真正调用 `splitChar` 的测试计算，可失败 —— 若字根表缺了某键、
或编码出现非法键位（如学习键 Z），门槛就会红。

### 教程：取码规则的组织方式与编码核对

教程共 9 章（`data/tutorial/ch01..09.md`），覆盖从「五笔是什么」到「重码与 Z 键」。
其中**取码规则**集中在四章，按「拿到一个字该走哪条分支」组织：

| 章 | 内容 | 对应规则 |
|----|------|---------|
| 5 | 单字取码规则 | 键名字 / **单笔画** / 成字字根 / 合体字 |
| 6 | 识别码 | 末笔所属区 × 字型 → 区内的第 1/2/3 个键 |
| 7 | 简码体系 | 一级 25 / 二级 605 / 三级 6412 |
| 8 | 词组规则 | 二字 / 三字 / 四字 / 多字 |

单字取码的四类判断顺序（第五章的核心）：

```
是键名字？（字根表每句口诀的第一个字）  → 连击该键 4 次
是单笔画？（一 丨 丿 丶 乙）            → 区首键 ×2 + L ×2
在字根表里？                            → 成字字根：报户口 + 一笔 + 二笔 + 末笔
其余                                    → 合体字：≥4 取 1,2,3,末；不足 4 补识别码
```

**「单笔画」必须单列**：一 丨 丿 丶 乙 这 5 个字虽然也是成字字根，
但取码规则不同（要补两个 `L`）。混在一起讲会推不出 `一 = GGLL` ——
而这正是最容易被问到的问题。`L` 是五笔的**补位键**。

> ⚠️ **成字字根不补位**。「十」只有两笔 → `fgh`（3 码）、「二」→ `fgg`，
> 有几笔取几码。只有那 5 个单笔画才补 `L`。

#### 教程里的编码断言是可核对的

教程中的编码统一写成 `[[码:字|编码]]` 标记，由 `tutorial-codes.test.ts`
**逐条与真实码表核对**（单字查 `chars.json`，词组查三张 phrases 表）。

为什么要专门做这件事：教程写错编码**不会影响编译、不影响练习**，
只会让学习者记住一个错的码 —— 这类错误没有任何机制会主动暴露。
实际核对下来，原有教程里就有多处：

| 位置 | 原写法 | 实际 |
|---|---|---|
| ch06 吧 | `kcg` | `kcn`（末笔是「折」不是「横」） |
| ch06 邑 | `kcf` | `kcb`（同上） |
| ch08 为什么 | `owtc` | `ywtc`（词组取码用**全码**首码，不是简码） |
| ch08 不好意思 | `dgvu` | `gvul` |
| ch03 键名字 | 「丝」 | 「纟」（`xxxx`；丝 = `xxgf` 是另一个字） |

其中 `ch08 为什么` 那个错最有教学价值：它正好示范了
**「词组取码只认全码，简码是单字专用的加速」**——现在教程把这点写成了显式警告。

核对规则（`isFullOrValidSimplified`）要允许三种情况，缺一不可：
1. 等于全码；
2. 等于 `simplifiedCode`（**必须单列**：一级简码不是全码的前缀，
   有 = `e` 而全码 `def`，我 = `q` 而全码 `trnt`）；
3. 是全码前缀且长度在 `[简码等级, 全码长度)` 内（`chars.json` 只存最短简码，
   而 会 → `wf`/`wfc`/`wfcu` 中 `wfc` 同样合法）。

> ⚠️ **一个必须记住的教训：验收指标要由「用户看到的那条路径」来算。**
>
> 旧版 `verify-wubi-split.mjs` 是 `.mjs`，无法 import TS，于是它只校验
> 编码格式（`/^[a-y]{1,4}$/`）就一律记 `resolved`，**恒报 100% / 0 / 0**。
> 而界面上 99.8% 的字显示「暂不支持」。两者差 500 倍，
> 却因为「脚本是绿的」而长期无人发现。
>
> 现在该脚本改为**委托** `splitter.coverage.test.ts` 并转发退出码。

## 6. 已知限制

| 限制 | 说明 |
|---|---|
| **仅支持 86 版五笔** | 98 版 / 新世纪版编码不同，不做切换 |
| **桌面优先** | 视口 < 1024px 时练习 / 复习 Tab 降级为只读，学习 / 查码 / 成绩仍可用；打字练习需要物理键盘 |
| **数据仅存本地** | 进度、错题、成绩都在 `localStorage`，不跨设备同步；清缓存即丢失（设置内可导出 JSON 备份） |
| **不挂载全局键盘监听** | 只在练习/复习 Tab 且会话进行中监听，避免影响页面其它输入 |
| **v1 不支持 Z 键（学习键）** | 键盘图上会展示 Z 键，但不参与编码 |
| **码表已按频次裁剪** | 极生僻字与长尾词组可能查不到；查码页会明确提示「未收录」而非显示空表格 |
| **文章练习仅内置篇章 + 自定义文本** | 无网络抓取 |
| **复习调度为简化 SM-2** | 非完整算法，按 1/2/4/7/15/30 天固定档位推进 |

## 7. 验收方式

```bash
# 一条命令跑通关键路径（CI 可用，失败非 0 退出）
bash scripts/check-wubi-tutor.sh

# 带后端时追加 HTTP 断言（未授权访问应返回 401/403）
API_BASE=http://localhost:8080 bash scripts/check-wubi-tutor.sh
```

脚本五段：

1. **路由注册与访问控制** —— 静态断言 `TOOL_WUBI_TUTOR` 已注册，可选 HTTP 断言
2. **构建物完整性** —— 4 个 JSON 的 `v` / `count` / `bucket` 字段与条目长度自洽
3. **拆字覆盖率** —— **`unsupported = 0`**（每个字的每一位都能给出键位与候选字根）；
   由 Vitest 中 import 真实算法的 `splitter.coverage.test.ts` 计算，脚本只做门槛判定。
   旧口径「`resolved` ≥ 95%」已废弃，原因见 §5「拆字演示」

   > ⚠️ 这个口径**测不出字根表缺字根**：它只问「码位对应的键有没有候选」，
   > 而每个键都有 ≥2 个字根，故恒为 100%。「正确的那一个字根在不在候选里」
   > 由 `data/radicals.test.ts` 的 `REQUIRED_RADICALS` 保证（见 §10 坑 7）。
4. **chunk 体积** —— 解析构建产物，与上表预算逐项对照；**并断言码表确为独立 chunk**
5. **静态检查 / 单测 / 类型 / Lint** —— 全部通过。静态检查含
   「字根展示完整性」：组件不得对 `radicals` 调用 `slice`、
   字根展示的 CSS 规则不得用 `nowrap` / `ellipsis`（理由见 §10 坑 5）

## 9. 视觉语言与材质令牌

基调是**「字根工坊 · 精密台面」**：汉字是纸上的墨迹，键盘是仪表盘，指标是量具。
落到实现上是一小组**材质令牌**（定义在 `.wt-page` 的令牌块内，浅色 / 暗色各一份）：

| 令牌 | 作用 | 用在哪 |
|---|---|---|
| `--wt-key-face` / `--wt-key-face-lit` | 键帽顶部渐变面（常态 / 受光态） | 练习页键盘、字根键盘图、空状态图标 |
| `--wt-inset-hi` | 1px 顶部内高光（「受光边」） | 所有凸起面：键帽、Tab 选中块、图标芯片、键位标记 |
| `--wt-key-drop` / `--wt-key-drop-hover` | 键帽投影（常态 / 悬浮） | 键帽、模式卡片 |
| `--wt-tray-bg` / `--wt-tray-inset` | 内凹托盘（底色 + 内投影） | 键盘容器、Tab 导轨、代码块、搜索框 |
| `--wt-paper-glow` / `--wt-paper-dot` | 宣纸质感：中心光晕 + 细点阵 | 练习题目台面 |

**三条必须遵守的规则**（都踩过）：

1. **键帽面用 `color-mix` 从 `--wt-bg-elevated` 推导，不要写死颜色。**
   写死 `#fff` / `#2a2a2e` 只对一套主题成立，另一套会变成脏边。
   浅色块里定义一次，暗色块**只覆盖透明度类令牌**（高光 / 投影），颜色类自动跟随。

2. **区色底是 JSX 内联的 `background-color`，内联优先级高于样式表。**
   字根图与图例要加受光，只能用 `background-image` 叠渐变，
   **不能**写 `background` 简写（会连同内联底色一起覆盖，键位变成无色）；
   同理 `border-color` 也改不动，选中态只能用外环 `box-shadow` 表达。

3. **`box-shadow` 是整体替换的。**
   状态类（`--target` / `--error` / `--pressed`）会覆盖基础规则，
   所以写 `@keyframes` 或 `animation: none` 时必须把
   `inset 0 1px 0 var(--wt-inset-hi)` 与投影一并带上，
   否则键帽在动画期间（或减弱动效下）丢掉内高光，退化成扁平描边方块。

动效统一在 `@media (prefers-reduced-motion: reduce)` 里降级为常亮状态。

## 10. 给后续维护者的提醒

按踩坑频率排序，以下问题在本模块**反复出现过**：

1. **Hook 里的闭包快照**
   「一轮多个事件 → 批量落盘」的场景必须提供批量 API，禁止在循环里调用
   单条写入函数 —— 同步循环内每次读到的都是同一份旧数组，后一次会覆盖前一次。
   已在 `useReview`（`answerReviewBatch`）踩过一次。

2. **`setState` updater 内做副作用**
   React StrictMode 会双调用 updater，导致重复落盘。
   副作用（读/写 localStorage）必须在 updater **之外**执行。

3. **`question.prompt` 不是「字」，`completedCount` 也不是「字数」**
   「题 ≠ 字」这个坑有两面，都要当心：

   - **prompt 的语义随模式而变**：单字模式是汉字，键位模式是键名
     （`"G"`），词组模式是 2~4 字词，字根模式是字根 glyph，文章模式是
     前 50 字摘要。而 `wrongChars` / `attemptedChars` 会被直接写进错题本
     （条目必须是**单字**，复习时要用它去码表查编码）。
     已用 `session.toReviewChar` 统一收口。
   - **「字数」一律走 `Question.charCount`**：单字 / 简码 = 1，
     词组 = 词组长度，文章 = 整篇可打字数，**键位 / 字根类 = 0**。
     键位 / 字根类练习的统计会回退成「按题计」；这条回退规则在四处
     各有一份（`computeSessionResult` 速度、`lessonDoneChars` 通关、
     `ResultPanel` 与 `MetricsBar` 的展示单位），改动时务必一起看，
     否则会出现「按字数判定通过、按题数展示成绩」的错位。

   新增题源时**必须声明 `charCount`**，否则该模式的成绩会被算成 0 字。
   同理准确率用 `wrongQuestionCount`（按题），**不要**改回
   `wrongChars.length`（按去重单字）——后者在字根 / 词组 / 文章模式下会算出「全对」。

   > ⚠️ 历史数据：`DailyStat.correctChars` 曾用「完成题数」填充，旧记录里
   > 键位 / 字根练习的字数被虚增、词组被少算。只影响历史累计值，
   > 不做迁移（迁移需要清空学习数据，代价大于收益）。

4. **`check-wubi-tutor.sh` 解析构建产物时不能按 `-` 切 chunk 名**
   rollup 的 hash 是 base64url，**本身可能含 `-`**（实测出现过
   `WubiTutorPage-Bfo1H2W-.js`）。脚本改用「已知名字 + 8 位 hash」精确匹配。
   这类 bug 的特点是**间歇性**：换了 hash 才失败，很容易被误判成偶发。

5. **「按容量截断」会把数据变成谎言 —— 同一类 bug 踩了 3 次**
   三处各自的写法与后果：

   | 位置 | 手法 | 后果 |
   |---|---|---|
   | `RadicalChart` 键盘格子 | `radicals.slice(0, 6)` + CSS `nowrap/ellipsis` | F 键 7 个字根只显示 6 个 |
   | `VirtualKeyboard`（练习页 / 复习页） | `radicals.slice(0, 5)` + CSS `nowrap/ellipsis` | 只显示 5 个，缺得更多 |
   | 两者的格子尺寸 | 固定 `height` + 单行 `max-width` | 字根多的键被整体裁掉 |

   共同特征是**JS 的阈值与 CSS 的容量恰好卡在同一个数**，于是看起来像
   「格子就这么大，显示这么多是正常的」——不像 bug，所以连续逃过了几轮 CR。
   但用户看到的是「字根表本身残缺」，会直接怀疑数据有错。

   规则：展示型截断一律改成**换行**（`min-height` + `white-space: normal`）；
   要完整阅读则提供专门的表格视图（`RadicalChart` 的「字根总表」）。
   键盘格子最多容纳 **8 个字根**（N 键），给某键新增字根前请先确认仍在 2 行内
   —— 上限断言在 `data/radicals.test.ts`（按「行数」而非「个数」表述）。

   守卫在 `check-wubi-tutor.sh` 第 5 段（**扫源码**：本项目没有 DOM 测试环境，
   渲染级断言做不了，而数据层的 `radicalsLabel` 单测只锁得住 helper，
   锁不住有人在组件里直接写回 `slice`）。

6. **日期与体积的「看似正确」**
   - 日期键统一用 `statsAggregation.toDateKey`（**本地时区**）。
     曾用 `toISOString()` 取 UTC 日期，导致 UTC+8 用户凌晨练习被记入前一天。
     同类问题还有 `addDays` 的「UTC 解析 + 本地格式化」混用 —— 只在负偏移时区暴露，
     建议 CI 追加一轮 `TZ=America/Los_Angeles npm test`。
   - 体积预算必须量**产物**，不能量原始 JSON（见 §3 坑 2）。

7. **「覆盖率 100%」不代表字根表完整**
   本模块的验收口径是「拆字覆盖率 `unsupported = 0`」，听起来很强，但它只
   检查「码位对应的键**有没有**候选字根」—— 每个键都有 ≥2 个字根，所以这个
   指标**恒为 100%**，无论字根表缺了多少字都测不出来。

   真实案例：字根表曾漏收 12 个常用字根
   （`辶 廴 冖 阝 母 具 乙 几 弋 丬 丿 攵`），其中「具 / 母 / 攵 / 乙」
   还是**本表自己的口诀点了名却没收录**的。后果不是「少显示一个字」，而是
   **拆字演示给出错误答案**：`splitter` 拿「该键的全部字根」当候选，
   `辶` 不在 P 的字根里，于是「这」的 P 段只显示「之/宀/礻/衤」，
   用户会以为算法坏了。

   判断口径：**口诀点名的字根必须在表内** —— 这是项目内的自洽性检查，
   比对照外部标准表更可靠，因为口诀就是本表对用户的承诺。
   守卫：`data/radicals.test.ts` 的 `REQUIRED_RADICALS`。

8. **reducer 里调用了会改状态的 `source.next()` —— 严格模式下每题多抽一次**
   本项目在 `main.tsx` 里开了 `<StrictMode>`，而 React 在严格模式下会
   **把 reducer 调用两次**（用于暴露不纯的 reducer）。`sessionReducer` 的
   `ANSWER` 分支直接调用 `handleAnswerKey(...)` → `source.next()`，而它会
   改写题源内部状态（`used` 集合 + 随机数发生器）—— 于是**每答一题，题源前进两次**。

   症状极其隐蔽：
   - 用户看到的题目顺序**完全正常**（多抽的那一题被丢弃），指标、进度也正常；
   - **单测全绿** —— 测试从不双调 reducer；
   - 只有在**中断恢复**时才暴露：`completed = 2` 的会话实际停在第 5 题上，
     于是「继续」恢复到相邻的题目（实测：刷新前「主」→ 继续后「晝」）。

   排查过程值得记一笔：先后被误导过三次 —— 怀疑过快照节流（实测 `pagehide`
   兜底 `savedAt` 与刷新只差 228ms，排除）、怀疑过种子错开（已把种子移入
   会话层，结构上排除）、直到发现「切掉 StrictMode 后同一场景两次全对」。

   规则：
   - **状态迁移不能放进 reducer**。`usePracticeSession` 现在用
     `useState` + 同步 `stateRef`（`applySession` 是唯一写入口）：
     迁移在事件回调里**只发生一次**，且读 `stateRef` 保证同一 tick 内的
     连续按键依次基于前一键的结果（不丢键）—— 这原本正是把迁移塞进
     reducer 的理由，两个目标现在同时满足。
   - 题源的**随机数发生器必须随 `init()` 重置**（`questionSource.ts` 各工厂
     的 `let rng` + `init` 内重置）—— 否则同一个题源被 `start()` 两次时
     题序会整体位移一格。
   - 验证这类功能**必须带着 StrictMode 跑**：双调是严格模式的行为，
     关掉 StrictMode 等于把被测条件删了（实测：关掉后同一场景全对，
     会得出「已修复」的错误结论）。

   新增字根时还有两点要注意：
   - 会改变拆字算法的分支：新字形若本身是汉字，会被当作**成字字根**走
     「键名码 + 首笔 + 次笔」规则。本次 12 个已逐个验证解释与真实编码一致。
   - **跨键重复**必须登记到 `radicals.test.ts` 的 `KNOWN_DUPLICATES`。

8. **错误提示给出的键，按下去必须被接受**
   错误提示条展示的是**出错那一位**的正确键（`getExpectedKey`），
   因此重试**不能回退输入**。`retryCurrentQuestion` 曾经把 `inputKeys`
   截断到「当前字符起点」（单字 / 词组模式即 0，整题重打），于是用户
   照着提示按下去，那一键会被拿去和第 1 位比较 → 立刻再判一次错、
   字符再次标红，同时已打对的前缀也被清掉。
   现在只清 `inErrorState`：错误键本来就不入队，位置原地不动。

   > 附带的同类坑：`PracticeBoard` 的错误闪动是**命令式**挂 `--error`
   > 类名 + 400ms 定时器摘除。只靠定时器复位不够 —— 用户在 400ms 内
   > 重试时，依赖变化会先触发 cleanup 清掉定时器，新一轮又走不到
   > addClass 分支，类名就永远留在元素上（「按错了后重按正确的还是标红」）。
   > 必须在 `inErrorState === false` 时**显式摘除**。

9. **文章模式里「一篇文章 = 一道题」**
   `skipCurrentQuestion` 结束的是**整篇**，不是当前字。因此凡是给文章模式的
   「跳过」入口都必须写成「跳过本篇」并交代后果 —— 标成「跳过」会让用户以为
   只跳过当前字，一点就把整篇丢了（实测确认过：点完直接弹成绩，完成题数 0/1）。

   当前字定位与「本字打了几码」由 `articleCursor.resolveArticleCursor` 解析
   （纯函数 + `articleCursor.test.ts`），**不要在组件里重新实现区间推导**：
   整篇编码被摊平成一维序列，每个字占 `[start, end)`，差一位的症状是
   「焦点条停在已打完的字上」或「最后一个字打完后焦点条空掉」——界面上
   只是一闪而过，肉眼抓不到。

   另外：文章练习里**所有字母键都是输入**，所以操作按钮不能绑字母快捷键
   （按 H 会被当作打字）。只标注真实存在的 `Ctrl + Enter`。

10. **新增设置字段必须同步 `normalizeSettings`**
    顶层 Tab 会持久化到 `settings.lastTab`，刷新 / 切走再回来都回到原处
    （否则在练习页一刷新就跳回学习页 —— 实测反馈）。

    ⚠️ `progress` 一直有 `normalizeProgress` 做字段级兜底，`settings` 却一直
    没有，于是任何后续新增的设置字段，在老用户数据里都是 `undefined`。
    现已补上 `normalizeSettings`，`loadAll` 与 `importData` 都走它 ——
    **以后往 `SettingsData` 加字段，必须在那里补一行**。漏了不会报错，
    而是界面直接渲染成空白，排查成本很高。

    另一条同源规则：**持久化的值一律不可信**，进 state 前必须过
    `normalizeTabKey`（以 `WUBI_TABS` 为唯一事实来源校验，非法值回退默认）。

    最后：**只持久化 `activeTab`**。`splitDemoChar` / `cheatSheetOpen` 是
    瞬时浮层，跟着刷新一起恢复的话，用户会看到一个自己并没有打开过的浮层。

   文章模式有两个视图开关，**都默认关闭**（由 ArticleBoard 自己维护）：

   - **键盘**（`keyboardOpen`）：高约 240px，展开会把正文挤到只剩两行。
   - **光标跟随**（`followCursor`）：它同时管两件事 ——
     ① 正文每敲一键滚到中间；② **键盘上的目标键高亮随之移动**。
     ② 最容易被漏掉：只停掉正文滚动却留下高亮，用户会发现「开关关了、
     键盘还在动」。开关放在键盘容器内（不在操作条），因为它管的主要是这张键盘。

   操作快捷键：**1 提示 / 2 看拆字 / 3 键盘开关**。能用数字键的前提是
   五笔编码只用到 `a~y`，而文章练习里**所有字母键都是输入**。
   ⚠️ 另一个前提：session 层把 `Digit1~5` 映射为「重码选择」，但那目前是
   **空实现**（`onSelectCandidate` 无操作）。将来真做重码选择时，这组快捷键
   需要重新分配。

   ⚠️ `settings.showVirtualKeyboard` 这个存储字段**目前没有任何消费者** ——
   `PracticeTab` / `ReviewTab` 都是写死 `true` 传下去的，
   `useWubiStorage` 的 `loadSettings` / `saveSettings` 也没有调用方。
   将来接设置面板时先把它接上，别以为它已经在生效。
